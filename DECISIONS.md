# Decisions log

Every choice that the Master Handover Pack does not settle, or that departs from it, is recorded here.
Authority order when documents conflict: 03, 02, 04, 05, 06, 01, 07 (Doc 00 §2).

## Approved by the product owner (conversation, 30 Sep 2026)

| # | Decision | Effect on the pack |
| --- | --- | --- |
| A-01 | Local-first PWA, works fully offline. | Doc 00 says "cloud-first" and Doc 05 §1 says "managed authentication". Both relaxed for V1. |
| A-02 | No login and no account system. Access is by license code (2 devices per code, one online activation, then offline). | Doc 05 §9 tenant isolation by user is not needed on-device. License module is designed separately (Doc 00 §4 excludes commercial entitlement). |

| A-08 | Work proceeds phase by phase. After each phase the developer reports and waits for approval. | Process. |

## Developer decisions (open for review)

| # | Decision | Reason |
| --- | --- | --- |
| D-01 | Stack: Vite, React 19, TypeScript, Tailwind v4, Vitest, vite-plugin-pwa, react-router (HashRouter). | Doc 05 §1 leaves the stack open. HashRouter and a relative base let the built app run from any static host or path, and offline. |
| D-02 | Inter is bundled with `@fontsource-variable/inter`, not loaded from Google Fonts. | Doc 04 asks for Inter. A CDN font would break offline use. Cost: about 200 KB of extra precache; can be trimmed to Latin subsets later. |
| D-03 | Placeholder PWA icons are generated by `scripts/gen-icons.mjs` (teal tile, three bars). | Doc 04 §2 says the logo is handled separately. Replace when the real logo exists. |
| D-04 | Mobile "Lagi" is a page (`/lagi`) for now, not a bottom sheet. | Keeps Phase 1 simple. Doc 04 §3 asks for a sheet, so this is revisited in the UI polish pass. |
| D-05 | Routes, nav order and labels follow Doc 02 §1 and Doc 01 §6. | Direct from spec. |
| D-06 | When something needed is missing or invalid, `computeMenuCost` returns an incomplete result that lists issue codes and only the components it could calculate. It omits full cost, profit and margin instead of guessing. | Doc 03 §8: never divide by zero, never assume zero overhead. |
| D-07 | A yield or selling price of zero or less is an incomplete state (`yield_invalid`, `selling_price_invalid`). | Both are denominators in Doc 03 §4 and §10. The spec does not name them. |
| D-08 | Expected sales of zero, missing or invalid is incomplete even if shared operating costs are also zero. | Strict reading of Doc 03 §8. Easy to relax if you prefer. |
| D-09 | Status comparisons allow a 1e-9 tolerance, so floating-point noise (for example −1e-16) is not called a loss. | Doc 03 §14 says to calculate at full precision. |
| D-10 | In Ruang Kerja, if both floor areas are given they decide the percentage, otherwise the manual % is used. | Doc 02 §7 says areas "derive" the percentage. |
| D-11 | Each Kos Operasi category is one row. `classification: direct` removes a row from the shared total. In Lebih Tepat, Elektrik holds only the remaining general shared amount; production appliances are costed per recipe. | Doc 03 §9 and Doc 02 §9. This is how the engine enforces "no double count". |
| D-12 | A negative value that rounds to zero displays as `RM0.00` with no sign. Display uses thousands grouping (`RM2,000.00`). | Doc 03 §14 preserves sign for real negatives. |
| D-13 | Pack-to-unit mappings (for example 1 pek = 12 biji) live on the ingredient and are optional. | Decision A-05. |
| D-14 | A custom scenario may be any finite percentage above −100%. | Doc 02 §12 lists "Custom" without limits. |
| D-15 | Reference fixtures split the Doc 03 §15 per-portion figures into real inputs (chicken RM15/kg at 120 g and 80 g). The sample chicken weights are invented for tests. | Needed to make M01/M02 and the chicken scenarios testable. |
| D-16 | Operating-cost detail (workspace, water, electricity) is embedded on the `OperatingCostRow`, with a unique `[businessId+category]` index. | One row per category and no duplicate on mode switch (Doc 06 §5); avoids separate detail tables to keep in sync. |
| D-17 | Derived values are never stored: ingredient/packaging unit cost, operating-cost rate, final monthly amount. `RecipeIngredient` has no cached cost. | Doc 05 §3 and §10: one authoritative source per value. |
| D-18 | A history record is appended when price, package quantity, package unit **or pack mappings** change (product owner confirmed, 30 Sep). Unit compared ignoring case/spaces; mappings compared ignoring order/case. Exactly one record per update. Each record stores the mappings in force. Name and active flag alone append nothing. | Doc 05 §5. Note: cost is normalised per package base unit, so a mapping-only change shows 0% on that basis and is flagged "mapping changed" instead of inventing a percent. |
| D-19 | `purchaseDate` defaults to the device's local calendar date, and can be set by the user (back-dating allowed). History is ordered by date, then by `seq`. Backfill uses the ingredient's `createdAt` date. | Malaysian users' "today" is local, not UTC. `seq` breaks same-day ties. |
| D-20 | Any non-blank unit is accepted as a package unit; unknown units are treated as counted units (for example `biji`, `kotak`). Blank units, non-positive quantities, negative prices and blank names are rejected before anything is written. | Custom counted units are normal in F&B. |
| D-21 | The database blocks updates and deletes on `priceHistory` (Dexie hooks) and enforces unique `[ingredientId+seq]`. | Doc 05 §5 immutability. |
| D-22 | Ingredient + history writes share one transaction; a failed history write rolls back the ingredient change. | No ingredient without history, no history without its ingredient. |
| D-23 | Numbers typed in forms accept a decimal point or comma ("15,5"), and a lone comma followed by exactly three digits is a thousands separator ("1,000"). Anything else is rejected with a message naming the field. | Malaysian users type both. |
| D-24 | Validation messages show after the first Simpan tap, then update live and clear as soon as the field is fixed. | Avoids nagging on an empty form while still guiding. |
| D-25 | Archive instead of delete for Bahan, Pembungkusan and Peralatan (with a "Tunjuk yang diarkib" toggle). No hard delete in V1. | Recipes (Phase 6) will reference these; deleting would orphan them. Archive never touches Jejak Harga. |
| D-26 | Equipment presets are seeded on first open and never overwritten. Choosing a preset copies its wattage as an estimate ("Anggaran UntungLab"). Changing the wattage, or tapping "Guna nilai ini", confirms it. Renaming alone does not. Custom equipment counts as confirmed. | Doc 02 §5, Doc 04 §5. |
| D-27 | Packaging has no price history in V1. | Doc 02 §4 and Doc 05 only require history for Bahan. |
| D-28 | Duplicate names are allowed (two ovens, two "Gula" brands). | A hard rule would block real cases; the user can tell them apart by size or archive one. |
| D-29 | Unit dropdown suggestions (kg, g, l, ml, biji, pek, kotak, botol, tin, ikat, keping) are hints only. The user can type any unit. | Matches D-20. |
| D-30 | Electricity tariff has **no built-in default**. The field shows "Contoh dalam spesifikasi UntungLab: RM0.50" as a hint only, and the user must save their own rate. Tariffs are effective-dated; the latest one not in the future applies. | The spec gives RM0.50 only as an illustration (Doc 03 §7). A silent default would put a made-up number into every user's cost. Until a rate is set, equipment electricity in a menu will be reported as incomplete (Phase 6). |
| D-31 | `WorkspaceDetail` gets an optional `method` ('percent' or 'area'). It says which input decides the business-use %; both the manual % and the areas are kept. Without it, the old rule (both areas present means areas decide, D-10) still applies. | Doc 04 §4 requires that switching back and forth never deletes advanced data. |
| D-32 | Nilai Masa may be RM0 (no labour costed); it can be left blank (not entered). Expected monthly sales must be more than RM0 or blank. Blank is stored as null and never read as zero. | Doc 03 §8. |
| D-33 | Onboarding is a "Mula di sini" checklist on the Dashboard route, with progress derived from saved data (Nilai Masa, Kos Operasi, Anggaran Jualan, first Bahan; Pembungkusan and Peralatan optional; first Menu shown as "tersedia tak lama lagi"). Business name and type are optional fields on the Kos Operasi page. There is no forced wizard. | Doc 02 §2 lists the steps; a checklist that reads real data cannot drift from what is saved. The real Dashboard arrives in Phase 7. |
| D-34 | In Lebih Tepat, Elektrik holds only the general shared amount (lighting, fridge, aircond). A visible warning tells the user not to include production appliances. Rows stay `shared` in the UI; the `direct` classification exists in the engine but is not offered in V1. | Doc 02 §9, D-11. |
| D-35 | Percentage chips are 10, 15, 20, 25 and "Lain-lain" for Ruang Kerja and Air alike. | Doc 02 §7 lists these for Ruang Kerja; §8 says "percentage chips plus custom input" for Air. |
| D-36 | The engine now reports, by name, anything the user has not set up: `nilai_masa_missing` (only when the menu has production time), `electricity_tariff_missing` (only when a used appliance has power and duration above zero), `packaging_missing`, `equipment_missing`, `operating_costs_invalid`. Nothing is guessed or skipped. Nilai Masa of RM0 is a real value. | Doc 03 §8 "never guess"; D-30, D-32. The Phase 2 engine assumed numbers were always present. |
| D-37 | A menu is edited as one screen and stored as Recipe + Menu (one-to-one) with child rows holding quantity, unit and duration only. Lines keep the order the user entered (`position`). No cost is stored anywhere. | Doc 05 §2, §3. |
| D-38 | Selling price 0 (blank) can be saved as a draft menu; the engine reports it incomplete. Yield must be more than 0 to save. | Lets the user save half-finished work without inventing a price. |
| D-39 | Menus can be deleted (with their lines). Master data (Bahan, Pembungkusan, Peralatan) still can only be archived; an archived item stays in existing menus, is still costed live, and is marked "(diarkib)". | D-25. |
| D-40 | The editor shows a live result from the unsaved form using the same assembler and engine as the saved list. A compact summary stays pinned at the top while lines are edited. | Doc 02 §10 result view; one engine for all screens. |
| D-41 | Unit choices for a Bahan line come from the ingredient: g/kg, ml/l, or the pack unit plus its mapped units. Any typed unit is still accepted; an unsuitable one is named as an incompatible unit, not converted. | Doc 03 §1. |
